# 看图回复流程（2026-10-04）

生产入口 `_deliver_job` → `open_image_and_reply`，辅助模块 `image_review.py`。

1. vision 事项由规划器强制设置 needs_image，带上原提问者。拟稿前复核可能滚动页面，因此重新截图并保存。缺坐标不再绕过图片检查。
2. 程序按像素连通区域产生候选红框与编号，扫描到底部消息区；模型按提问者、问题和上下文选择唯一候选，不按最大图或旧坐标选择。候选不足时允许模型给框，但必须额外查看实际裁剪，证明裁剪就是目标图片。多图歧义转机主。
3. 点击前确认屏幕未变，打开后同时读全屏和目标裁剪，核对同一张图。若明确有查看原图/原视频按钮，核对按钮后点击，有限等待加载；加载状态未知、失败或仍有原图按钮都停止。没有原图按钮只记 viewer_ready_no_original_button，不声称已获取原始分辨率文件。
4. 回答需要的酒标/小字不清楚时双击放大，额外核对仍是同一处且确实放大。先生成可见事实、文字和不确定项，判断信息足够后才使用运行时人设生成回复。视频仍抽多帧，不把首帧当完整视频。
5. 看图失败清空缩略图答案，暂停该事项，走已有飞书确认单；没有拟答不能照发。机主明确提供措辞后可沿用既有确认流程。API 有既有超时和供应商退避，加载/放大不无限重试。
6. 看图后返回群再观察，沿用事项修订和发送前复核。成功证据连同缩略图指纹、发送者、事实、修订号和最终回复保存在 job payload。仅同一任务修订、同一回复复用缓存；旧版 _used_image 不作为已看清证据。没有跨群缓存复用。

防止模型误读的检查仍由视觉模型参与，不保证零误判。看图成功与微信群实际发送是两个状态，发送仍需绿色气泡/输入框/数据库回执验证。

验证：17 项图片专项回归，覆盖原图加载、坐标缺失、坐标缩放错误、点错图片、多图歧义、发送者不匹配、放大失败、不清晰及修订缓存。原有 85 项相关回归以及 11 项问答/联网证据回归通过，共 113 项。真实群截图定位回放单独记录，不向群发送测试消息。
