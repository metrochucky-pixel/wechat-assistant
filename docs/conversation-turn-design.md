# 多人群聊判断设计

2026-09-30。基于当前 wechat_autoreply.py 和 bot_reliability.py 的设计稿；本稿不表示运行中的 bot 已具备这些新能力。

目标：回答真正找自己的、仍然需要回答的事情；合并补充，识别插话，及时接受更正，并允许选择沉默。自然感首先来自回复对象、内容和时机正确，再由现有人设决定措辞。

## 当前需要改变的地方

- process_one_conversation 目前先取 OUTBOX.next，有任务便直接进入发送流程；有未到重试时间的任务便返回。因此旧任务可能阻止采集新补充、新问题或纠正。
- last_customer_msg 和 need_reply 仍以整屏决策为中心，缺少每条消息的发送者、回应对象与话题关系。
- pending_questions 有完整问题，但没有稳定的提问者 ID、问题版本或独立授权事件。Outbox.add 按问题文字合并，可能混淆不同人问的同一句话。
- mentions 是群级线索；应与具体直接 @ 消息事件区分。发送前目前检查“本人已答/明确取消”，还需识别其他群友是否已实质解答，以及问题条件是否已改变。

保留现有会话核验、草稿保护、图片匹配、发送事务和不确定结果核对。此次设计不调整会话列表的坐标偏移参数。

## 流程

核对会话 → 采集新增消息 → 更新各个问题 → 应用群规则 → 判断回应价值与时机 → 生成候选回复 → 重新采集并核对版本 → 使用原发送事务发送。

采集优先于出队。有旧问题处于接口冷却时，仍然保存新消息；发送结果不确定时可以继续采集，但暂停该会话的后续发送，先核对上一次结果。

## 三层数据

1. 消息事件 message_events

记录 conversation_id、event_id、sender_key、可见昵称、原文、引用对象、直接 @ 对象、首次/最后观察时间、画面顺序、来源截图片段、识别不确定项。实际消息时间与观察时间分开；看不见时间不编造。

当前通过截图读取，event_id 是本地事件编号，不冒充微信原生消息 ID。用连续截图的重叠消息顺序、发送者、内容和气泡证据对齐。同文消息不按全文哈希永久合并；无法辨别旧消息还是新消息时保存歧义，暂不发送。昵称不清楚时不用猜测身份或关系。

2. 话题与待答事项 topics / requests

话题聚合同一件事；待答事项记录具体在向谁回答。字段包括 request_id、topic_id、requester_key、source_event_ids、完整问题、已知条件、未解决子问题、revision、addressing_evidence、authorization_event_ids、answered_by、state、first_seen_at、last_relevant_update_at。

同一个人的连续补充更新同一事项的 revision。不同人问相同内容保留各自 request_id，可以共用一次回答，但不能共享直接 @ 授权。

3. 候选回复 response_candidates

记录 reply_to_request_ids、reply_to_event_ids、收件对象、用到的问题版本、群策略版本、内容、证据来源、生成时间、有效期及当前采集序号。接入现有 outbox，保留其发送确认职责。

## 模型判断与程序约束

视觉提取负责“谁说了什么”；规划模型负责“在回应谁、属于哪件事、是否需要我接话”。模型输出结构化建议和原文证据，不能直接调用发送。

规划动作限定为：补充已有问题、纠正已有问题、新建问题、已被回答、取消、需要澄清、暂等、忽略。每个动作必须引用已存在的 event_id / request_id；不存在的引用、错误类型或无法确认的身份不能生成发送任务。无需用一个不可校准的模型置信分数决定是否发言。

程序强制检查会话、黑名单、群策略、授权事件、任务状态、问题版本、消息是否已处理、节奏限制和发送事务。聊天内容不能修改这些规则。

只有确定要回复时才加载现有人设生成答案，避免为了写一句有趣的话而倒推“必须插话”。一般一轮只生成一个最值得回答的候选；同话题多人受益时可在一条回复中覆盖多个已获授权事项。

## 场景规则

| 场景 | 行为 |
| --- | --- |
| A 连发“新加坡读书”“本科”“偏计算机” | 合并为一项，保留三个条件，答一次 |
| A 问学校，B 插入喝酒玩笑 | 玩笑不覆盖学校任务，也不延长学校任务的收集等待 |
| A 问学校，B 问另一件事 | 建立两个事项，分别判断是否向我提问及优先级，不机械逐句回复 |
| A 和 B 都直接 @ 我问同一个问题 | 可以合并作答，分别绑定两个授权事件和两个事项 |
| B 已给出正确、足够的回答，A 表示解决 | 将该事项标为 resolved_by_other，正常情况下不复读 |
| B 只猜测或只回答一半 | 保留未解决部分；有可靠补充才回复 |
| A 说“不是本科，是硕士” | 更新条件、版本加一，废弃旧版本的候选答案 |
| A 说“不用了” | 取消该事项；已经点发送且结果不确定的事务仍先核对，不篡改为未发送 |
| 群里有人说“你怎么看”，但指向不明 | 不把所有“你”理解成 bot；普通群必要时简短澄清，严格 @ 群等待明确直接 @ |
| 有人发“哈哈”、表情、互相寒暄 | 通常沉默；普通群仅在明确接自己的话且有回应价值时简短接一次 |

“别人已经回答”需检查回答针对的是同一个问题、是否覆盖关键条件，不能只检测到任意一条回复就取消原任务。对于需要查证的事实，不凭另一位群友的自信语气认定正确。

## MentionOnly 授权边界

- 列表的“有人 @ 我”仅用于发现消息；发送许可来自已核实的具体新直接 @ 事件。
- 旧 @、引用内 @、@所有人、@别人、提到昵称都不构成许可。
- 一次 @ 只授权回答所关联的请求，不能开启几分钟的任意聊天窗口。
- 原提问者在回答前补充同一问题，可以合并进原授权事项；出现新的独立问题，仍需新的直接 @。
- 原请求已回答后，不因别人普通接话就继续发言。旧请求仍未解决时，相关补充可更新任务；与其无关的消息不能搭便车入队。
- A 的授权不能代替 B 的授权。同一条合并回复只覆盖已分别获得授权的事项。
- 完成、取消只消费相应授权事件，不能删除整个群的其他待答 @。

## 何时回复

下列数字是第一版可调整参数，不是实测最优值，也不是端到端响应时间承诺。

- 首次发现问题进入 collecting；最后一次相关补充后约 4–8 秒作为候选合并窗口。接口读取本身已经超过窗口时，不额外固定睡眠。
- 持续有人补充时，单次收集最多约 15 秒，然后评估已有完整问题；无关话题不得不断重置等待时间。
- 明确且简短的直接提问可减少等待；明显未说完、连续发条件时优先等补充。
- 调度用 next_eligible_at，让出手机给其他群，不在主循环里 sleep 等待该群安静。
- 排序采用：明确直接找我、尚未完成的承诺/问题、普通群明确接我的话、可选闲聊。相同等级按等待时长轮转，避免一直饿死旧问题。
- 普通群闲聊初始限制为约 30 秒内最多一次；明确不同人的直接提问可以排队回答，仍遵守原发送节奏。不是按群里总发言量增加 bot 发言次数。
- 玩笑、寒暄等低时效事项过时后可静默取消；明确的问题不因时间过去自动当成已答，应重新判断、保留或转人工。

## 发出前的更新检查

模型计算期间手机继续收到消息，必须再次采集并更新事项。

- 只有无关插话：原问题未变，可以发送，开头点明对象或问题。
- 新增限制/纠正：revision 改变，废弃旧候选，重新生成或补查。
- 明确取消或已得到充分回答：取消候选。
- 收件对象/授权事件/群身份不确定：暂缓发送。
- 原问题滚出画面：使用已保存原文，不能拿最新闲聊代替；但仍检查当前可见的纠正、取消和已有回答。无法覆盖生成期间的消息缺口时，不声称已完成全面更新核对。

发送提交前在同一事务中验证候选的版本仍等于当前事项版本。生成完成不等于回答完成，仍以现有 outbox 的发送确认作为完成依据。屏幕观察无法与微信服务端做到原子同步，需明确保留这一限制。

自然的对象提示可用“鹏飞，你刚才问的新加坡本科……”或“接你刚才那个学费问题……”。身份已核实时才使用名字；普通文字中的 @ 不是微信真正的提及操作，不用假 @ 冒充选中群成员。

## 代码落点与实施顺序

1. 新增 conversation_events.py：纯数据的事件去重、截图重叠对齐和 sender 证据；修改 read_and_decide，把逐条提取与回复规划拆开。
2. 新增 conversation_planner.py：事项归并、版本更新、是否应答、优先级和合并窗口。规则用纯函数；模型建议通过严格 schema 校验后进入这些规则。
3. 扩展 SQLite：新增消息、话题、事项、授权事件、候选回复表。旧 outbox 继续负责交付；不把群级 has_mention 直接迁移成所有事项的授权，也不自动重放历史聊天。
4. 修改 process_one_conversation：先采集/更新，再选择待答事项。取消“有旧任务便绕过新消息采集”的短路；把 outbox 的交付状态与聊天判断状态分离。
5. 将 reply_to_request_ids、revision 和授权证据交给 _deliver_job；在现有草稿/身份检查前完成新消息核对。sending/uncertain 仍禁止盲重发。
6. 先对匿名化对话片段进行离线回放；随后影子规划只记录与旧路径的差异、禁止发送。涉及手机的采集仍是唯一执行者，不能让两套循环同时操控手机。验收通过后按群启用新规划器，MentionOnly 的严格授权条件始终有效。

第一版保持单进程、单手机执行者。若进一步将 API 计算放到后台，工作者只能处理数据和返回带版本的候选，不能操作 ADB；现有 signal 总超时不能原样搬进工作线程，需使用可终止进程或明确的异步取消方案。

## 验收

- 连续三句补充产生一个事项、一条回答，条件完整。
- 多人交错发言正确归属，不把某人的学历、预算套给另一人。
- 旧任务冷却期间仍采集到新问题、更正和取消。
- 回答生成期间“本科改硕士”，旧版本永不进入发送提交。
- 不同人同文问题不被全文哈希吞掉；同一旧截图不重复入队。
- 其他人真正解决问题时不复读；只接梗不算解决知识问题。
- MentionOnly 无授权事项发送数为零，A 的 @ 不授权 B；完成 A 后 B 的待答 @ 保留。
- 发送结果不确定和重启不造成重复回复。
- 观察消息不完整、发送者未知时能暂缓，不猜测未见的群聊历史。

记录每次选择的对象、事项、依据事件及“为什么回答/等待/跳过”，用于人工回放评估。不要以发言量、拟人语气或单个模型自评分作为成功指标。
